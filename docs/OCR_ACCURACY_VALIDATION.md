# PHASE 9 OCR 정확도 검증

## 정답과 측정 방식

`tests/ocr_benchmark_fixtures.py`는 가상 신고번호와 품목 정보로 PDF 10개와 정답 JSON을 생성한다. 정상 전자 PDF, 필수 수치가 없는 문서, 복수 라인, 정정 갑지·을지, 일반·저해상도·회전·혼합 스캔, 손상 및 암호화 PDF가 포함된다. 정답 값은 PDF 생성 시 함께 지정하며 OCR 결과에서 가져오지 않는다.

`epms.ocr_benchmark`는 정답과 비교해 정확, 오입력, 미인식, 명시적 공란의 허위 추출, 누락·중복 품목 및 문서 단위 일치를 집계한다. 날짜, 금액, 신고번호는 EPMS 비교 규칙을 적용한다. 예를 들어 `1,200.00`과 `1200`은 같은 수치이며, 품목 번호 `001`과 `1`은 추출 시 서로 다른 표기로 취급한다. 여러 품목은 같은 쪽의 고유한 신고번호와 품목란이 모두 일치할 때만 대응시킨다. 정답에서 명시한 `null`은 원본에 값이 없음을 뜻하고, 생략한 필드는 해당 사례의 채점 범위 밖이다. 출력에는 실제 원본값이 없다.

```powershell
python tests/ocr_benchmark_fixtures.py build/phase9-benchmark
python -m epms.ocr_benchmark build/phase9-benchmark/truth.json --methods legacy direct windows hybrid
```

합성 문서 생성에는 개발 환경의 ReportLab과 로컬 한글 폰트를 사용했다. Windows OCR이 포함되는 시험은 허용된 PowerShell 세션에서 실행한다. 실제 업무 PDF의 정답 JSON은 로컬에서 작성하며 저장소에 넣지 않는다.

## 합성 평가 결과

| 구분 | 기존 정규식 | PDFium 직접 | Windows OCR | 하이브리드 |
| --- | ---: | ---: | ---: | ---: |
| 전자 PDF 4개·품목 5개 | 3/38 | 38/38 | 29/38 | 38/38 |
| 일반 스캔 | 0/8 | 0/8 | 7/8 | 7/8 |
| 저해상도 스캔 | 0/8 | 0/8 | 0/8 | 0/8 |
| 항공화물운송장 혼재 스캔 | 0/8 | 0/8 | 7/8 | 7/8 |
| 회전 스캔 | 0/8 | 0/8 | 7/8 | 7/8 |

하이브리드 경로의 전자 PDF 정확일치율과 자동입력률은 각 38/38, 문서단위는 4/4였다. 스캔 정확일치율과 자동입력률은 각 21/32(65.63%), 미인식은 11/32(34.38%), 문서단위는 0/4, 품목 식별 일치는 3/4였다. 일반·혼합·회전 스캔에서 누락된 필드는 HS코드였다. 저해상도 표본은 약 58 DPI로 생성했으며 8개 모두 누락됐다. 합성 하이브리드 채점 범위에서 잘못 채운 값과 명시적 공란의 허위 입력은 없었다. 혼재 항공화물운송장은 후보를 만들지 않았고, 손상·암호화 PDF는 두 건 모두 거절됐다.

invoice2data 실증은 현재 환경에서 승인된 wheel을 확보하지 못해 표에 포함하지 않았다. Windows 언어팩 제거 상태의 실기 시험도 남아 있다. 기존 정책 제한 시 복구 가능한 OCR 오류 안내는 앞선 시험에서 확인했다.

## 실제 스캔과 화면 응답시간

수정에 직접 사용하지 않았던 로컬 스캔 PDF 1개(3쪽)에 Windows OCR을 실행했다. 2쪽에서 신고필증 서식 후보와 품목란 번호가 나왔다. 신고일자, HS코드, 순중량, FOB 후보는 각각 1쪽에서 확인됐다. 신고번호 후보는 없었다. 이 표본은 실제 값의 정답이 없어 인식 여부만 집계했다.

Microsoft Edge에서 별도 SQLite 테스트 DB로 각 합성 파일을 처음 업로드하고 FOB 입력칸이 나타날 때까지 측정했다. 전자 PDF 134ms, 일반 스캔 1,868ms, 저해상도 1,855ms, 혼합 1,857ms, 회전 1,845ms였다. 유형별 단일 관측이며 필드가 공란이어도 검토 화면이 열린 시점을 기준으로 했다. Python 회귀시험 89건과 Playwright 업무 흐름 7건이 통과했다.

## 라이선스와 ZIP

기존 Lite와 Portable ZIP을 읽기 전용으로 조사했다. SBOM에 기재된 DLL·EXE·PYD·JS는 각각 133개와 172개가 일치했다. 고지 파일이 참조하는 로컬 원문은 각각 95개와 96개가 모두 있었다. 별개로 양쪽에 원문 미확보 표시가 1건씩 있었고, 라이선스 식별자 보류 표시는 각각 19건과 20건이었다. 이 결과는 저작권과 필수 NOTICE 의무의 법적 검토를 완료했다는 뜻이 아니다. 검사에서 PDF·운영 DB 포함 여부를 확인했으며 새 배포본은 생성하지 않았다.

합성 표본의 정확도는 실제 신고필증에서의 개발 목표 달성을 입증하지 않는다. 독립 수기 정답이 있는 실제 전자·스캔 PDF로 업체명, 사업자번호와 여러 서식의 필드 정확일치율을 별도로 평가해야 한다.
