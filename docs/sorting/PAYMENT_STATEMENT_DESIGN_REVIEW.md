# 공동선별비 지급명세·지급확정·중복지원 방지 설계 검토

2026-11-23 최신 보완: 외부 결재액, 분할/합산 지급, 환수·입력 정정, 증빙, 개인별 결과 명세와 같은 DB 거래 중복 방지를 구현했다. 아래 미구축 판정은 당시 기준 및 전자승인·자동지급 경로에 관한 것이다. 상세는 [PAPER_WORKFLOW.md](PAPER_WORKFLOW.md), 최신 검증은 IMPLEMENTATION_STATUS.md를 따른다.

후속 구현 안내: 아래는 기능 추가 전 검토 당시의 판정이다. 이후 회원별 귀속/검토 지급명세와 검토용 지급 준비 대장을 구현했다. 현재 사용법은 BENEFICIARY_STATEMENTS.md 및 PAYMENT_PREPARATION.md, 최신 검증은 IMPLEMENTATION_STATUS.md를 따른다. 실제 보조금 승인·지급 확정/회수 원장이 미구축이라는 운영 판단은 유지한다.

작성일: 2026-11-23. 현재 소스의 테이블·서비스·API·Excel/인쇄 함수 및 기존 시험 항목을 읽어 검토했다. 이번 작업은 설계 검토이며 신규 지급 기능을 구현하거나 운영 지급을 활성화한 결과가 아니다. 이번 검토에서 전체 시험이나 실제 은행 대사를 재실행하지 않았다.

## 판단

현재는 신고 품목란 ↔ 작업/출고의 다대다 물량 연결과 신청별 검토 출력까지 구현되어 있다. 생산자 회원사별 공동선별비 보조금 지급명세, 확정 지원금의 행별 귀속, 실제 보조금 지급 결과 확정 및 지급 후 재신청 차단은 미구현이다. 선별장/생산자별 확정 지급명세를 지금 출력할 수 있다고 판단하면 안 된다.

기존 PAYMENT_HISTORY는 선별비용 발생액에 대한 과거 이체증빙 기록이다. 통합조직 → 수혜 회원사 보조금 지급 거래가 아니다. PRODUCER_SETTLEMENT의 농산물 거래 정산도 보조금과 분리되어 있고 government_subsidy/refund는 미확정이다. 이 세 자금 흐름을 같은 완료 상태로 합치면 안 된다.

지원금 수령인이 생산자 회원사인지, 시설 운영자·다른 적격 주체인지 및 농가 귀속/환류 방식은 P-01·10·11·12 등의 확정 근거가 필요하다. ‘시설 소유 회원=실제 원물 생산자=보조금 수령인’을 기본값으로 두지 않는다. 생산자 식별 문자열을 회원 명부의 검증된 수혜자로 자동 간주하지 않는다.

## 권장 데이터 구조

지급명세의 최소 세부 단위는 다음 연결을 추적할 수 있어야 한다.

사업/정책 버전 → 신청 배분행 → 신고번호·품목란·유효 버전 → 시설·작업·출고 → 생산자 원물/검증된 귀속 근거 → 적격 수혜 회원 → 비용 배부 → 승인 지원금 → 지급 회차·은행 거래 배부.

한 표에 모든 항목을 중복 저장하기보다는 다음 별도 원장을 추가하고 외래키로 연결한다. 아래 명칭은 제안이며 현재 구현 테이블이 아니다.

1. **수혜자 귀속 원장**: allocation_id, 검증된 beneficiary/member 참조, facility/batch/dispatch/intake 참조, 귀속 물량, 귀속 근거 증빙, 판정 버전. 혼합 LOT은 생산자별 수출 적합량과 손실/내수 배분 근거까지 확인한다. 여러 수혜자 분배가 제도상 허용될 때에만 분할을 허용한다.
2. **행별 비용 귀속 원장**: expense_id, 세부 귀속행, 시설·품목·비용 귀속월, 배부 금액, 분리 근거. 기존 신청 단위 배부만으로는 복수 시설·월·생산자별 금액을 확정할 수 없다.
3. **지원 결정 원장**: 정책 버전·한도 그룹·심사 근거 snapshot, 인정 물량·적격 비용·승인액, 수혜자별 승인 명세, 승인자. 원본 변경으로 자동 덮어쓰지 않는다.
4. **보조금 지급 원장**: 지급 묶음/회차, 수혜자·승인 명세별 지급액, 지급예정/실제 지급일, 계좌 참조, 거래 ID·세부 순번, 증빙, 등록·확인자, 상태. 기존 비용 PAYMENT_HISTORY와 분리한다.
5. **물량·비용 점유 원장**: 지원 대상 부분의 고유 식별과 RESERVED/COMMITTED/CONSUMED/RELEASED 등 상태 이력. 신청 ID나 수혜자만 바꿔도 같은 물량/비용을 재사용할 수 없도록 원본 자원에 연결한다.
6. **정정·환수 원장**: 원 지급 참조, 변경 이유·근거, 조정 결정, 실제 회수 거래, 잔액. 환수 완료가 지원대상 물량의 재사용 허가를 뜻하지 않는다.

원물·증빙이 없는 기본형 기록은 회원별 귀속을 새로 입증해야 한다. 기본형 작업의 총 kg을 회원수로 나누거나 기존 직접·간접실적 비율을 가져와 확정하면 안 된다.

## 명세서 설계

출력은 같은 고정된 결정/지급 버전을 기준으로 세 종류를 제공한다.

- **회원사 교부용**: 해당 수혜자만 표시. 사업연도·정책·명세번호·회차·회원명, 신고번호/품목란, 시설·작업기간, 본인 귀속량 kg, 적용 산정 근거, 승인액·이번 지급액·누적 지급액·미지급 잔액·실제 지급일. 계좌는 마스킹하고 다른 회원 자료는 제외한다.
- **사무국 지급대장**: 회원/시설/귀속월별 소계와 지급 묶음 합계, 실제 거래별 배부, 보류·실패·재이체·잔액. 업무 권한에 따라 상세 접근을 제한한다.
- **신고필증별 추적명세**: 신고번호·품목란·정정 버전별 물리 순중량, 연결된 각 시설/작업/생산자 귀속과 지급 명세 참조. 다른 회원에게 같은 신고 순중량 전체를 반복 인정하지 않았는지 확인한다.

Excel과 PDF/인쇄는 동일한 출력 데이터 모델을 사용한다. 명세 번호·버전·원 지급 참조를 고정하고, 재출력은 새 지급으로 기록하지 않는다. 지급예정 명세는 ‘지급예정/미지급’, 실제 지급 확정 명세는 실제 지급일·거래 근거를 표시한다. 현재 REVIEW_ONLY에서는 ‘검토용/지급 미확정’ 초안만 허용한다.

### 수량 예시 (가상)

신고 품목란 D1 1,000kg 중 시설 A 작업 600kg, 시설 B 작업 400kg이 연결되어 있고, 시설 A의 같은 작업 원량 900kg 중 나머지 300kg이 D2에 연결되었다고 가정한다.

| 신고 품목란 | 시설 | 실제 배분량 |
| --- | --- | ---: |
| D1 | A | 600kg |
| D1 | B | 400kg |
| D2 | A | 300kg |

D1은 1,000kg, A 작업은 900kg만 집계한다. D2의 나머지 신고 가용량은 다른 예약/원본으로 따로 확인한다. 이 세 행에서 실제 수혜 회원의 귀속 근거를 추가한 후 금액을 산정한다. 단가·보조율·비용·절사·한도가 미확정이므로 이 예시에서 지급액을 만들지 않는다.

## 지급 확정 버튼의 올바른 의미

‘승인’과 ‘실제 지급 확인’을 분리한다. 기관이 정하는 권한에 따라 독립된 사용자/직무분리를 적용하고, 현재 단일 PC 토큰이나 자유 입력 이름을 인증으로 간주하지 않는다.

권장 흐름은 검토 → 승인/물량·비용 확정 점유 → 지급예정 명세 → 외부 은행에서 실제 송금 → 결과·증빙 등록 → 확인권자의 지급결과 확정 → 지급완료 명세이다. 자동 송금 구현을 요구하는 설계가 아니다.

실제 송금 뒤 버튼을 누르는 동안만 중복이 막히는 구조는 부족하다. 승인 또는 지급 준비 시점에 자원을 먼저 잠그고, 송금 결과 미확인 중에도 점유를 유지해야 한다. 실패가 확실히 확인된 경우에만 재시도를 허용하며, 보조금 수혜 권리는 그대로 두고 실패 지급 회차만 처리한다.

확정 모달은 대상 회원·회차·이번 금액·누적액·잔액·실제 지급일·거래 참조·증빙·확인자를 표시한다. 버튼은 **실제 지급결과 확정**으로 명명하고, ‘송금 요청’으로 오인하지 않게 한다. 일반적인 입력 수정/취소와 구별해 정정 경로를 제공한다.

서버의 단일 transaction에서 아래를 검사한다.

1. 확정 정책/운영 권한/증빙 등 운영 게이트 및 현재 결정 버전이 유효한가.
2. 승인·수혜자·계좌 참조·금액이 등록한 거래 배부 및 증빙과 맞는가. 계좌번호만으로 수혜자를 식별하지 않는다.
3. 동일 요청키의 재전송인가. 같은 키/본문은 같은 결과를 반환하고, 키가 같고 내용이 다르면 거절한다.
4. 동일 은행 거래의 동일 세부 지급항목이 재사용되었는가. 한 거래를 여러 승인 건에 합산 지급한 정상 사례는 거래별 배부 합계로 통제한다.
5. 회차·승인 명세별 확정액과 진행 중 지급액의 합계가 승인 한도를 넘지 않는가. 동시 클릭·다른 창에서도 검사한다.
6. 물량/비용 점유 상태가 적법하게 이전되는가. 같은 부분을 예약과 지급완료 양쪽에 이중 집계하지 않으며, 지급 완료 후 일반 철회가 이를 해제하지 못하게 한다.
7. 변경 전후·확인자·시각·사유·근거 버전을 기록하고 전부 성공하거나 전부 취소한다. 로컬 관리자에 대한 진본 보증 수준은 별도 인증/감사 설계가 필요하다.

부분 지급은 동일한 승인 명세의 금전 잔액만 줄인다. 두 번 나눠 송금한다고 해당 수혜 물량을 두 번 지원한 것으로 생성하지 않는다. 지급액 0이나 송금 실패를 ‘지급완료’로 일괄 처리하지 않으며, 별도의 결정 취소/불지급 종결은 정책에 따른다.

## 중복 방지 범위와 계산 제약

- 신고 품목란의 동일 물리 물량은 모든 관련 신청/회원/시설의 미해제 점유와 소비를 함께 검사한다. 부분 물량 식별자를 새로 만들었다는 이유로 원량 한도를 늘리지 않는다.
- 동일 작업·출고·입고 기원과 동일 비용 증빙을 별도 신청·별도 시설 ID·파일 재업로드로 우회하지 못하도록 자원 계보/증빙·거래 식별을 함께 대사한다. 파일 해시만으로 서로 다른 문서의 동일 비용까지 모두 찾아낸다고 보장하지 않는다.
- 중복 지원 범위는 사업/연도 간 정책에 맞춰 적용한다. ‘사업연도가 다르니 같은 물량 재사용 가능’ 또는 ‘모든 타 사업 일률 금지’를 기본값으로 정하지 않는다.
- 여러 PC의 독립 SQLite 파일에는 공통 transaction이 없으므로 실시간 중복 방지를 보장할 수 없다. 단일 권위 원장 사용을 원칙으로 하거나, 승인된 동기화·충돌 차단·지급 전 최신 외부 원장 검증 절차가 필요하다. 불명확하면 지급 보류한다.
- 지원액은 승인 산식과 비용/한도 단위에서 산정한 후 행별 배부한다. 원 단위 절사·잔액 배분은 정책으로 정하고, 결정적으로 재현 가능하게 한다. 신청 분할로 한도/반올림을 유리하게 바꾸지 못하도록 그룹 전체를 함께 검사한다.
- 명세 세부 합계=회원 소계=지급 묶음 합계, 실제 거래 배부 합계=거래 금액을 검증한다. 세액·환류·공제는 승인 기준이 있는 경우에만 반영하고, 다른 성격의 농가 거래 공제를 임의로 상계하지 않는다.

## 구현 권장 순서 및 인수 기준

1. **수혜자·자금 흐름 확정**: 수령 주체·혼합 LOT 귀속·비용/한도/환류·중복범위·절사·지급 권한·공식 서식 근거 확보. 미확정 항목은 보류한다.
2. **세부 귀속/비용 배부와 검토명세**: 기존 예약을 유지한 채 additive migration으로 귀속 원장을 추가. 기본형 미확인과 혼합 원물의 미확정 귀속을 명시. 검토용 회원별/시설별/신고별 Excel·인쇄를 먼저 구현할 수 있다.
3. **승인 불변본과 지급예정 점유**: 인증·직무분리·운영 게이트가 충족된 경우에만 연결. 지급 확정은 아직 켜지 않는다.
4. **보조금 지급 결과/회차·거래 배부·확정**: 기존 비용 이체이력과 분리하고 과거 지급 이관 시에도 검토 이력과 운영 확정 이력을 구분한다. 기지급 자료 미반영 상태에서 전체를 신규 가용량으로 열지 않는다.
5. **정정·부분 지급·실패/재이체·환수와 실제 기관 인수**: 원본 정정 및 재사용 정책까지 검증 후 운영 전환한다.

필수 시험은 1:1/1:N/N:1/N:M, 복수 품목란/시설/월/수혜자, 혼합 원물 귀속 누락, 비용 중복 배부, 그룹 절사/분할 한도, 부분 지급, 합산 송금, 실패 재시도, 동일 요청 재전송·변조·동시 확정, 거래 참조 중복·원본 변경·계좌 불일치, 지급 후 철회/삭제 차단, 정정/환수 후 자동 재사용 차단, 재출력 불변, 회원 교부본 개인정보 분리, 기존 직접·간접실적 회귀이다. 실제 은행 증빙·운영 검증 사본과 기관 담당자의 인수 결과는 합성 시험으로 대신하지 않는다.

현 단계에서 버튼을 추가해 기존 SUBMITTED/COMPLETED 또는 PAYMENT_HISTORY를 지급 완료로 재해석하는 방식은 채택하지 않는다. 기존 검토 전용 차단을 유지하면서 세부 귀속 명세부터 개발하는 것이 다음 구현 단위이다.
