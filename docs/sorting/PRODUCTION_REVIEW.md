# 복수 원물 선별과 잔량 검토 (2026-11-23)

OCR과 독립적인 마스터 M3 생산 편집 보완이다. M1의 실제 증빙 전수 대사·기관 인수는 여전히 진행 중이다. 신규 테이블·migration·의존성을 추가하지 않고 기존 sorting_records와 sorting_batches 및 배분 원장을 사용한다. .git이 없는 작업 사본이며 기준 SHA/브랜치/HEAD는 확인 불가이다. 원격 push·공개 release·운영 DB 적용은 하지 않는다.

## 사용법과 계산 기준

비용·거래·생산 → 등록할 검토 기록 → 선별·재선별을 선택한다. 시설을 고른 뒤 같은 시설·품목의 입고와 이전 작업을 여러 건 추가하고 사용량을 편집·삭제한다. 작업번호·작업일·증빙 ID와 적합/내수/비상품/감모/보류 재고량을 입력한다. 소수점 6자리까지 원값을 보존하며 다섯 출력량의 합이 투입량과 같아야 한다. 수출 적합량이 0이면 새 수출 작업을 만들지 않는다. 보류 재고는 이월 재사용할 수 없다(POLICY_PENDING).

원장 표는 검색 및 50행 페이지 이동을 지원한다. 입고 잔량은 입고량−후속 작업 투입량이다. 작업 잔량은 등록량−후속 작업 투입량−출고량−출고를 통하지 않은 활성 예약량이다. 출고분과 연결된 예약은 출고 때 이미 차감되어 두 번 빼지 않는다. 반려·철회된 직접 예약은 다시 가용해지지만 실제 출고는 예약 해제와 무관하게 계속 차감한다. 음수 잔량을 0으로 숨기지 않고 충돌로 표시한다. 등록 원장 계산이며 실제 생산 물리 추적이나 수출 이행 확인을 뜻하지 않는다.

## 서버 검증과 재전송

GET /api/org/{org}/sorting/production-ledger는 조직 내 입고/작업별 원본번호·날짜·증빙 ID·소비량·잔량을 십진수 문자열로 반환한다. PDF OCR 내부 캐시는 생산 조회에서 제외한다. 기능 기본 OFF와 기존 세션/조직 범위를 유지한다.

POST transforms/dispatches는 BEGIN IMMEDIATE 안에서 재검증한다. 작업번호/출고번호는 각각 조직 안에서 고유하다. 같은 번호·같은 요청의 재전송은 기존 ID를 반환하며 차감·작업·감사 기록을 추가하지 않는다. 같은 번호의 다른 내용은 SORT_E09/409로 거절한다. 원물 순서 변경도 다른 요청이므로 등록 후에는 새 번호를 사용한다. 기존 기록은 덮어쓰지 않는다.

복수 투입은 같은 원물이 반복되어도 합산하여 상한을 검증한다. 다른 조직·시설·품목 혼입, 원물 입고일/선행 작업일보다 이른 작업일, 음수/과도한 정밀도, 수지 불일치, 기존 직접 예약/출고/후속 작업을 포함한 잔량 초과를 거절한다. 중간 실패 시 전체 transaction을 rollback한다. 입고 품목도 시설 품목과 일치해야 한다. 화면 잔량은 참고이며 저장 시 서버 검사 결과가 기준이다.

## 규칙과 시험 근거

BR-201/202/203/207/305/601~603의 기술 보완이다. 구현은 epms/sorting_production.py, sorting_api.py 및 web/sorting-production.tsx, sorting-operations.tsx이다. tests/test_sorting_production.py는 복수 입고 병합·소수 6자리·반복 원물 합산 초과·출력 없는 작업 재전송·실패 rollback·날짜 역전·다른 조직·품목 차단·직접 예약과 출고 예약의 비중복 차감·철회 복구·동시 경쟁을 검증한다. tests/browser/sorting.spec.ts는 두 입고 선택, 수량 편집, 저장 및 서버 잔량을 검증한다. 단계 전체 PASS나 정책 승인을 의미하지 않는다.

정책 P-01~15 미승인과 독립 사용자 인증/직무분리 부재로 승인·신규 보조금 지급·공식 지급 출력은 계속 차단한다. 실제 원물·기관 ERP·이월·복잡한 혼합 LOT·기관 PC 및 네이티브 창 인수는 별도이다. OCR 환경 확인은 사용자 진행 항목이며 이번 변경은 실행 정책이나 OCR 엔진을 변경하지 않는다.
