# UI·UX 및 기능적 사용자경험 감수 보고서

감수일: 2026-11-28 (한국 시간)
대상: 현재 소스와 dist 웹 빌드, 공동선별 기능 활성 상태
판정: **초보 사용자 단독 업무 인수는 보류. 중요 결함 보완 후 재감수 필요.**

## 1. 감수 범위와 근거

격리 복사한 합성 DB에서 Edge 브라우저로 14개 메뉴를 확인했다. 기본 화면은 1366×768에서 조사하고, 주요 화면은 1280×720, 820×950, 500×900에서도 확인했다. 화면 캡처, 실제 계산된 글자/버튼 크기, 입력 보존과 이동, 잘못된 숫자 붙여넣기, 계약 검증 결과, 월별 보고서 보존·다운로드를 조사했다.

대상 메뉴는 업무 안내, 회원사, 계약, 선별장, 선별기록, 신고필증, 정산 진행 현황, 정산 작업, 지원기준·배정, 월별 보고, 연간 수출실적, 보관함, 설정, 도움말이다. 메뉴 단위 관찰은 모든 조건·모든 버튼·모든 데이터 규모를 전수 검증했다는 뜻이 아니다. 실제 초보 사용자를 모집한 사용성 시험과 정식 접근성 인증은 수행하지 않았다. 연간 수출실적은 시험 DB의 정책 미등록 안내 상태를 확인했으며, 이번 감수에서 연간 Excel 확정·다운로드까지 새로 검증하지는 않았다.

제품 코드는 수정하지 않았다. 시험 자료와 감수 증거만 생성했다. 운영 DB는 열거나 변경하지 않았다. Windows 배포 EXE의 네이티브 창·설치·업데이트는 이번 브라우저 감수 범위 밖이다. 기존 release/v202 ZIP은 11월 26일, 최신 dist는 11월 28일 자료이므로 감수 결과를 기존 배포본 전체에 적용할 수 없다.

증거는 `output/ux-audit`에 보관했다. `pages.json`, `responsive.json`, `functional-probes.json`, `deeper-probes.json`, `contract-state-evidence.json`, `button-feedback.json`과 화면 캡처가 재현 근거다. 정상 메뉴 관찰과 최종 보고 시나리오에서 수집된 JavaScript 오류는 0건이다. 이는 업무 정확성이나 모든 예외 경로의 무결점을 뜻하지 않는다.

## 3. 우선 보완해야 할 사항

P1은 업무 오류·입력 손실·핵심 정보 식별 위험 때문에 우선 처리할 항목이다. P2는 업무를 끝낼 수 있어도 반복 오류와 문의를 유발하는 항목이다. P3는 후속 품질 개선이다. 아래는 실제 관찰과 코드 확인에 근거한 감수 판단이며 자동화 도구의 심각도 점수가 아니다.

### UX-01 [P1] 미검토 계약을 최종 검증 근거로 사용할 수 있음

**재현:** 계약 목록에 `유효 · 미검토`인 계약이 있다. 이 계약과 당사자·기간이 일치하는 신고는 계약 검증에서 문제 없이 통과하며 계약 ID/차수가 근거로 반환된다. 같은 상태를 사용하는 합성 정산의 확정과 월별 제출본 보존도 성공했다.

**원인:** `epms/member_contracts.py:103`의 assess는 기간 중심으로 유효성을 계산한다. `epms/contract_gate.py:37`은 이 유효 상태만 확인하고 계약의 review를 확인하지 않는다. 제조자 미대조 D091 차단을 추가한 이전 수정만으로 이 경우가 해결되지는 않는다.

**영향:** 사용자는 미검토를 아직 확인되지 않은 계약으로 이해하는데 시스템은 확정 근거로 사용할 수 있다. 요청했던 ‘표준계약서 관계 확정 전 차단’의 의미와 충돌할 가능성이 높다.

**보완:** 기간 유효, 원문 검토, 당사자 관계 확인을 별도 상태로 정의한다. 최종 확정에 어떤 확인 상태가 필요한지 업무 기준으로 명시하고 서버·화면·일괄 입력에 공통 적용한다. 임시 저장은 허용한다. 검토가 필요 없는 것으로 업무 결정한다면 ‘미검토’ 표기와 ‘확정 가능’ 안내를 그 결정에 맞게 고쳐야 한다.

**인수 기준:** 미검토·확인 필요·확인 완료·해지·기간 만료·자기 수출의 상태별 확정 허용 표가 있고, 실제 확정 API와 화면이 모두 같은 결과를 보여야 한다. 기존 확정본을 임의로 소급 변경하지 않는다.

### UX-02 [P1] 미저장 입력 보호가 화면마다 다름

**재현:** 선별장 신규 등록에서 이름을 입력한 뒤 ‘목록으로’ → ‘신규 등록’을 누르면 경고 없이 빈 값이 된다. 계약 신규 등록에서 계약명을 입력한 뒤 왼쪽 신고필증 메뉴로 이동해도 경고가 없다. 반면 회원사 화면의 조사 경로에서는 변경 취소 확인이 나타났다.

**원인:** 선별장 신규 화면은 미저장 상태를 추적하지 않는다. 계약은 자체 열기/닫기와 브라우저 종료는 보호하지만 공통 WorkflowProvider의 dirty 등록은 하지 않는다.

**보완:** 신규·수정·PDF 첨부에 공통 미저장 상태와 ‘저장하고 이동 / 계속 작성 / 버리고 이동’을 적용한다. 목록, 메뉴, 뒤로가기, 작업/연도 전환을 같은 규칙으로 처리한다. 파일 업로드 완료와 입력 저장 완료는 구분한다.

**인수 기준:** 선별장·계약·회원사·신고·선별기록·지원기준·보고서에서 미저장 이동과 복구를 각각 확인한다. 409/422/서버 연결 실패 후에도 입력·첨부 선택을 유지한다.

### UX-03 [P1] 매칭 화면은 CSS 글자 크기보다 실제 표시가 훨씬 작음

**실측:** 1366×768에서 SVG scale이 약 0.64997이다. 카드의 11px 생산자·날짜·잔량 안내는 실제 화면에서 약 7.15px, 15px 제목은 약 9.75px로 표시된다. 원문 버튼은 약 41.5×15.9px다. 일반 화면도 본문·표·입력·버튼이 12px 중심이다.

**영향:** 실수 방지에 필요한 날짜·업체명·물량을 읽기 어렵고 확인 없이 연결하기 쉽다. CSS의 font-size만 높여도 작업판 전체를 축소하면 같은 문제가 남는다.

**보완:** 기본 본문/입력은 16px 전후, 보조 안내는 14px 전후를 제품 가독성 목표로 삼는다. SVG 축소로 텍스트를 줄이지 말고 최소 실제 글자 크기를 유지한다. 일반 업무용 노트북에서는 ‘후보 표 + 연결 상세’를 기본으로 하고 그래프는 보조 보기로 제공하는 방안을 권장한다. 주요 버튼은 높이 40~44px, 연결점도 충분한 클릭 면적을 제공한다.

**인수 기준:** 1366×768·1280×720의 기본 확대율에서 생산자, 날짜, 물량을 확대 없이 읽고 선택할 수 있어야 한다. 키보드만으로도 후보 선택·연결·해제·저장을 끝낼 수 있어야 한다. 200% 확대 검증은 추가로 수행한다.

### UX-04 [P1] 일부 중요한 보조 문구의 명도 대비가 낮음

**실측:** 매칭 상세의 11px 문구 `rgb(106,127,115)`와 배경 `rgb(247,250,252)`의 대비는 약 4.09:1, 잔량 안내 `rgb(117,136,123)`는 약 3.60:1이다. 비활성 장식이 아닌 실제 생산자·잔량 정보다.

**보완:** 실제 표시 색으로 일반 텍스트 4.5:1 이상을 확보한다. 회색/녹색의 채도를 낮추는 대신 명도를 충분히 낮추고, 차단·보완·완료는 색뿐 아니라 문구·아이콘으로 구분한다.

12px라는 사실 자체가 WCAG 위반을 의미하지는 않는다. 위 글자 크기 목표는 업무 사용성을 위한 감수 권고이고 대비 기준은 별도다.

### UX-05 [P2] ‘지원액 확인’ 단계가 실제 화면 상태를 전환하지 않음

**재현:** 정산 작업 1을 연 뒤 4단계 ‘지원액 확인’을 누르면 `/sorting?stage=calculate`로 이동하지만 계산 기준은 펼쳐지지 않는다. 새로고침하면 작업 선택도 빈 값으로 돌아온다.

**원인:** workflow 단계는 stage 파라미터를 만들지만 settlement 화면은 이를 처리하지 않고 링크도 job ID를 보존하지 않는다.

**보완:** `job`과 `stage`를 URL에 함께 보존하고 해당 계산 요약/기준 패널을 열어 포커스를 이동한다. 작업이 없으면 새 작업 화면에 조용히 보내지 말고 작업 선택을 안내한다.

**인수 기준:** 3→4→5단계, 새로고침, 뒤로가기 후에도 같은 작업·월·보고서를 가리켜야 한다.

### UX-06 [P2] 필수/선택 항목의 구분과 초보자용 기본 화면이 부족함

**관찰:** 회원사 신규 입력은 14개 입력/선택 칸을 전면 노출하며 필수 표시가 없다. 서버는 회원사명·사업자번호·유형·가입승인일 등을 요구한다. 계약 신규 입력은 조사 시 보이는 입력 컨트롤만 28개다. 선별장 폼은 일반 inline 배치라 ‘지정 종료일’ 라벨이 줄 사이로 갈라지고 화면 아래의 넓은 공간을 활용하지 못한다.

**보완:** 기본 화면은 해당 업무를 저장/매칭하는 데 필요한 항목만 보여준다. 주소·대표자·연락처·조항 전문·메모는 선택 상세에 둔다. 필수 표시는 서버 규칙과 일치시키고 날짜 입력 방식·단위를 명시한다. 선별장은 2열 폼과 상단 라벨, 하단 저장 영역으로 재구성한다.

선택 항목이 실제로 강제된다고 단정하는 것은 아니다. 현재 문제는 선택 항목도 필수처럼 전면에 노출되어 사용자가 모두 채워야 한다고 오인하기 쉽다는 점이다.

### UX-07 [P2] 저장 버튼 비활성화 이유와 실패 후 보완 동선이 불충분함

**재현:** 신규 월별 보고서에서 작성자를 입력하지 않으면 ‘보고서 저장·점검’이 비활성화된다. 해당 필드의 필수 표시와 버튼 인근 사유는 없다. 지원기준은 변경 사유를 입력해야 저장 버튼이 켜지고 계약은 PDF·당사자 조건이 버튼 비활성화로 표현된다. 조건은 코드에 있지만 화면만으로 찾기 어렵다.

**보완:** 임시 저장과 최종 점검을 분리하거나, 저장 시 누락 목록과 첫 필드 이동을 제공한다. 작업 중 중복 클릭 방지를 제외한 비활성화에는 바로 옆에 구체적 이유를 표시한다. 새 선별기록의 필드별 오류 안내를 공통 패턴으로 확장한다.

### UX-08 [P2] 숫자 붙여넣기가 잘못된 값을 조용히 만들 수 있음

**재현:** 선별물량에 `1.234,56`을 넣으면 오류 없이 `1.23456`으로 표시된다. 쉼표를 무조건 지우므로 `1,23` 같은 잘못된 묶음도 정상 숫자처럼 취급할 수 있다. 또한 계약 거래금액은 `1234567.89` 그대로 표시되고, 월별 내부결정액 등 일부 필드도 공통 숫자 입력 적용 대상에서 빠져 있다.

**보완:** 숫자 의미를 바꾸는 정규화를 하기 전에 허용 형식을 검증한다. 천 단위 쉼표·소수점이 모호하면 해석값을 확인시키거나 오류를 표시한다. 금액/중량 필드 타입으로 컴포넌트를 선택하고 한국어 라벨의 정규식으로 숫자 필드를 추측하지 않는다. 문자열/Decimal 정밀도 보존은 유지한다.

**인수 기준:** `1,234.56`, `1234.56`, `1,23`, `1.234,56`, 음수, 0, 빈 값, 소수 끝 0, 큰 수를 화면·API·재조회까지 일관되게 처리한다.

### UX-09 [P2] 단일 회원사 지급에서도 동일 금액·증빙을 여러 번 다루게 됨

**관찰:** 합성 5,000원·회원사 1개 보고에서 결재문서 총액, 결의의 회원사 배분액, 거래 전체 금액, 지급의 회원사 배분액을 각각 보여준다. 내부결정액·이번 보고 귀속액 등도 별도 단계에서 관리한다. 내부결정 후보 자동 채우기와 지급 명세 가져오기는 이미 제공된다.

**판단:** 내부결정·지출결의·실제 지급은 서로 다른 사건이라 원장상 구분이 필요하다. 필드를 모두 없애는 것은 적절하지 않지만, 담당자가 같은 정상값을 반복 입력해야 하는 UX는 줄일 수 있다.

**보완:** 단일 회원사·전액 배분일 때는 거래금액에서 배분액을 자동 제안한다. 당사자·기본 작성자·제출처·공통 증빙은 재사용하고, 다회원 분할·일부 지급·환입·차이만 직접 보완하게 한다. 자동 제안과 원문 확인을 구분한다.

### UX-10 [P2] 오류 사유가 작고 좁은 내부 스크롤에 갇힘

**관찰:** 신고 원장 편집기는 폭이 제한되고 오류 설명 버튼은 높이 4.5em와 내부 스크롤을 가진다. 긴 계약 차단 문구의 일부만 보인다. ‘다음 오류로 이동’과 필드별 상세는 도움이 되지만 초보자가 둘의 관계를 먼저 알아야 한다.

**보완:** 상단에는 ‘계약 없음 / 제조자 미대조 / 날짜 오류’처럼 한 줄 원인, 바로 옆에 ‘계약 등록하기 / 회원사 선택’ 동작을 둔다. 긴 설명은 펼칠 수 있게 한다. 보완 화면에 기존 신고번호·품목란을 유지하고 저장 후 원래 점검 결과로 돌아오게 한다. D091 등 신규 차단 코드는 연간 제출 화면의 공통 계약 안내에도 빠짐없이 연결한다.

### UX-11 [P2] 다운로드 파일명이 문서의 종류·월·차수를 설명하지 않음

**재현:** 실제 월별 제출본 다운로드의 제안 파일명이 `공동정산 수출실적 관리.pdf`였다. 서버는 `filename="monthly-report-1.pdf"`를 보내지만 클라이언트는 filename*의 UTF-8 형식만 읽고 나머지는 공통 이름으로 대체한다.

**영향:** 여러 월의 보고서와 정산 결과를 파일 탐색기에서 구별하기 어렵고, 이전 파일을 제출하는 실수에 취약하다.

**보완:** filename*와 filename을 모두 처리한다. `2026-07_사과_공동선별비_제출본_1차.pdf`처럼 월·품목·종류·확정 차수를 포함하고 초안/보존본을 구분한다. ZIP도 같은 이름 규칙을 사용한다.

### UX-12 [P2] 작은 화면에서 가로 넘침이 없어도 실제 업무는 어려움

**관찰:** 1280/820/500px 조사 경로에서 문서 전체 가로 넘침은 없었다. 그러나 500px 매칭 작업판은 최소 너비 780px 때문에 오른쪽 후보를 내부 가로 스크롤로 찾아야 한다. 전체 정산 페이지는 약 3,185px 길이였으며 이 값은 데이터와 열린 패널에 따라 달라진다. 고정 계산 도크는 좁은 화면에서 작업 영역을 더 줄인다.

**보완:** 작은 화면에서는 선별 선택 → 신고 후보 목록 → 연결 확인의 순차 화면을 제공한다. 내부 가로 스크롤이 필요한 경우 방향과 숨겨진 후보 수를 표시한다. 고정 도크는 본문과 겹치지 않게 공간을 예약하고 상세 패널·키보드 포커스가 도크 뒤에 가려지지 않는지 검사한다.

### UX-13 [P3] 시작 안내·도움말·상태 용어가 실제 새 업무 전체를 설명하지 못함

**관찰:** 도움말의 주요 순서는 설정·회원사·신고·연간 제출의 4단계에 머물러 선별·매칭·지원기준·월별 지급보고 흐름을 설명하지 않는다. ‘초안’, ‘원문 확인’, ‘연결 준비 완료’, ‘연결 확정’, ‘제출본 보존’, ‘제출 기록’이 서로 다른 화면에 분산되어 있다. 선별장 제목도 외부/내부 두 번 반복된다.

**보완:** 처음 한 번 필요한 회원사·계약·선별장·지원기준을 체크리스트로 안내하고, 매일 하는 입력과 분리한다. 현재 자료/작업의 상태와 다음 행동을 한 곳에서 보여준다. 실제 제출과 파일 다운로드를 계속 구분하되 긴 기술적 표현은 짧은 업무 용어와 보조 설명으로 나눈다.

## 4. 유지할 장점

- 선별장 목록 우선 구조와 종료일 미정 처리는 업무 흐름에 맞는다.
- 선별물량은 생산자·일자·물량·PDF 중심이고, 제목/번호를 자동 생성하며 OCR을 강제하지 않는다.
- 선별기록의 필드별 누락 안내·오류 요약·입력 유지 방식은 다른 폼에도 확장할 만하다.
- 신고 목록은 통과/확정 차단을 명시하고 계약 보완 링크를 제공한다.
- 물량의 양쪽 잔량과 확정 전 재검증, 과거 PDF 보존이라는 구조는 유지해야 한다.
- 대표 기본 버튼은 눌렀을 때 translate 1px, scale 0.98, 배경색 변화가 실제 적용되고 해당 목록 이동도 정상 실행됐다. 눌림 애니메이션 자체를 새로 만드는 것이 우선 과제는 아니다.
- 별도 합성 자료로 월별 보고의 점검 통과 → 제출본 생성·보존 → 브라우저 다운로드를 완료했다. 내려받은 PDF는 6쪽이며 목차 항목 2개를 확인했다. 이 감수에서 PDF의 모든 시각적 페이지 품질을 새로 인수한 것은 아니다.

## 5. 입력 항목별 정리 원칙

| 업무 | 기본 노출·직접 확인할 항목 | 자동화·선택 상세로 옮길 항목 |
| --- | --- | --- |
| 회원사 | 이름, 사업자번호, 역할, 가입승인일 | 연락처, 주소, 대표자, 별칭, 메모 등 |
| 선별장 | 이름, 지정번호, 시작일, 운영 회원사, 지정 PDF | 종료일·주소·위탁주체는 선택 표시 |
| 선별기록 | 생산자, 선별일/기간, 수출용 물량, 단위, PDF | 조직/품목/시설 상속, 제목/번호 자동, 부가 물량은 선택 |
| 계약 | 당사자, 실제 기간/체결일, PDF, 관계 확인 상태 | 조항 전문·선택 금액·메모는 필요한 경우 펼치기 |
| 지원기준 | 연도, 적용 기간, 단가/보조율, 예산, 기준 근거 | 고급 허용차·다중기간·전환 검토는 별도 관리 |
| 지급보고 | 실제 의사결정·결의·지급 사건의 식별 정보 | 단일 회원 배분·기본 작성자·제출처·정상 합계는 재사용/자동 제안 |

필수 항목을 삭제해 서버 검증을 우회하는 방향은 권하지 않는다. 필요한 사실은 유지하고 기존 정보 재사용, 안전한 기본값, 예외만 추가 입력하는 방식으로 부담을 줄여야 한다.

## 6. 보완 순서와 재감수 통과 기준

1차는 UX-01 계약의 확인/유효/확정 의미, UX-02 입력 보존, UX-03~04 실제 가독성과 대비다. 업무 오류와 입력 손실에 직결되므로 먼저 처리한다.

2차는 단계 URL과 작업 복원, 공통 폼의 필수/선택·저장/오류 패턴, 숫자 형식·파일명 일관성이다. 3차는 단일 회원 정상 처리의 자동 채움, 작은 화면 대체 흐름, 도움말과 온보딩이다.

권장 인수 기준:

- 기본 노트북 해상도에서 날짜·금액·업체명을 확대 없이 읽고 핵심 동작을 완료한다.
- 200% 확대에서 내용과 기능을 잃지 않는다. 이는 후속 실제 확대 시험으로 확인한다.
- 14개 메뉴의 미저장 변경 보호를 공통 시나리오로 확인한다.
- 비활성화된 핵심 버튼은 이유와 해결 행동을 제시한다.
- 조회·저장·검증·보존·실제 제출의 상태를 구분하며, 완료 메시지는 서버 결과와 일치한다.
- 한 회원사·전액 지급 사례는 같은 금액을 반복 타이핑하지 않고 완료할 수 있다.
- 오류 보완 후 기존 작업·신고·월로 복귀한다.
- 초보자 3~5명을 대상으로 ‘선별기록 등록→다음 달 신고 매칭→지급보고→파일 찾기’를 설명 없이 수행시킨다. 완료율·중도 포기·잘못된 클릭·도움 요청·재입력 횟수를 기록한다. 현재 감수는 이 사용자 시험을 대체하지 않는다.
- 최신 EXE/ZIP을 별도 시험 DB로 실행해 같은 수정이 실제 배포본에도 포함되었는지 확인한다. 버전·빌드 날짜를 사용자가 화면에서 확인할 수 있어야 한다.

## 7. 참고 기준

WCAG 2.2의 일반 텍스트 대비 4.5:1 기준과 200% 글자 확대 시 기능 보존 기준을 참고했다. 클릭 대상의 최소 크기에는 간격/동등 기능 등의 예외가 있으므로 작은 연결점만으로 전체 접근성 실패를 단정하지 않았다. 일반 버튼 40~44px와 본문 16px는 이 제품의 사용자를 고려한 감수 권고다.
